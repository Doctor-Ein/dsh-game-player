# 游戏定位工具设计文档

> 记录日期：2026-11-01
> 背景：给 PC 接了虚拟副屏 + Sunshine/Moonlight 串流之后，打绝区零时发现"点击不准"，
> 一路排查下来定位到了真正的需求：**需要一个能给出精确坐标的定位工具**。
> 本文档汇总问题、现状、和希望实现的方案。

---

## 一、要解决什么问题

### 表面现象

点击游戏里的按钮，落点总是偏。有时候点不中，有时候打开了旁边的东西。

### 真实原因（排查后的结论）

**不是坐标转换有 bug，而是"我读不出准确的像素坐标"。**

现在的链路是这样的：

```
游戏画面 → game_shot 截图 → 我（模型）看图 → 目测估计按钮在第几像素
         → 心里乘缩放比 → 得到坐标 → game_do 点击
```

问题出在中间那一步：**我盯着图片"看"，然后凭感觉报一个数字。** 这对小按钮完全不够用。

实测证据（今天连续三次都没点中「入梦」按钮）：

| 我估计的坐标 | 来源 | 结果 |
| --- | --- | --- |
| `(2380, 1340)` | 大致方位 | 没中 |
| `(1440, 850)` | 1:1 原图上读的 | 没中 |
| `(1063, 622)` | 从缩放宫格反算 | 没中 |

同一个按钮，三次读数三个结果，**全都错**。而大目标（关卡卡片）因为面积大，估个大概也能点进去——这就是"有时候能用"的原因。

## 二、环境现状（已实测）

### 显示器与缩放

```
主屏（物理显示器）  2560 × 1440 物理像素
                    2048 × 1152 逻辑像素   ← Windows 缩放 125%
                    DPI = 120
                    刷新率 180 Hz

虚拟副屏（VDD）     1920 × 1080
                    位于主屏【左侧】，x 从 -1920 到 0
                    缩放 100%

虚拟桌面（合起来）  3968 × 1152（逻辑）
                    左上角 (-1920, 0)
```

### 关键认识：两块屏的缩放不同

```
主屏：   2560 物理 → 2048 逻辑   (÷1.25)
虚拟屏： 1920 物理 → 1920 逻辑   (÷1.00, 无缩放)

所以 1920 + 2560 ≠ 3968（物理相加），
    而是 1920 + 2048 = 3968（逻辑相加）
```

**这是所有混乱的根源。** 任何"按物理像素相加"的直觉在这里都会出错。

### 游戏窗口

```
绝区零窗口位置：(0, 0)
窗口客户区：2560 × 1440（物理） / 2048 × 1152（逻辑）
```

窗口正好在主屏左上角，所以 `(0,0)` 既是客户区原点，也是主屏原点。
这也是为什么"以前没接副屏时一切正常"——那时两种坐标恰好重合。

## 三、现有的坐标机制（按代码现状）

### 三个环节，三套口径

| 环节 | 代码位置 | 用的单位 |
| --- | --- | --- |
| 读窗口尺寸 | `win32.ps1` → `Get-WindowInfo` | **逻辑像素**（`GetClientRect` 原值） |
| 截图 | `eyes.ps1` → `Capture-Frame` | **物理像素**（`CopyFromScreen` 本来就抓物理像素），边界用 `GetSystemMetrics(0/1)` = 逻辑值 |
| 发鼠标 | `win32.ps1` → `MouseMoveAbs` | 按 `GetSystemMetrics(0/1)`（**主屏逻辑尺寸**）归一化 |

### 三个具体的隐患

**隐患 1：截图边界用主屏尺寸裁剪**

```powershell
$swW = [Gp]::GetSystemMetrics(0)   # 2048（主屏逻辑宽）
if (($x + $w) -gt $swW) { $w = $swW - $x }   # 把超过 2048 的宽度砍掉
```

窗口物理宽 2560 > 2048，**会被砍成 2048**。
（实测中截图尺寸有时是 2560×1440，说明这条路径不是每次都触发，但它是确定的 bug。）

**隐患 2：`MouseMoveAbs` 的分母是主屏，不是虚拟桌面**

```csharp
int sw = GetSystemMetrics(0), sh = GetSystemMetrics(1);   // 2048 × 1152（主屏逻辑）
int nx = (int)Math.Round(x * 65535.0 / (sw - 1));         // ← 按主屏归一化
```

但 `SendInput` 的绝对坐标（`MOUSEEVENTF_ABSOLUTE`）是**按整个虚拟桌面**解释的。
虚拟桌面宽 3968 ≠ 主屏宽 2048，**分母错了**。

**隐患 3：截图坐标 ≠ 点击坐标（大问题）**

我给 `game_do` 的 `x/y`，理应和截图里量的位置是同一套单位。
但实际上：截图是物理的，`MouseMoveAbs` 按逻辑的主屏尺寸归一化，**中间没有任何换算**。
所以要"点中"，我得在脑子里做一次混合换算——而这件事我做得不可靠。

### 今天试过的修复（已回滚）

我改过 `win32.ps1` / `run.ps1` / `eyes.ps1`，思路是"全部统一到虚拟桌面物理像素"。改动包括：

- `MouseMoveAbs` 改用 `GetSystemMetrics(76..79)`（虚拟桌面）归一化
- `Get-WindowInfo` 输出物理尺寸（乘 DPI 缩放）
- `Capture-Frame` 边界改用虚拟桌面矩形

**回滚原因**：改完之后反而更不稳定——手进程反复断连、点击完全无反应。
而且回滚后原版能点中 Combat-2（大目标），说明**原版在多屏下并非完全不可用**，
问题被我的改动放大了，而不是解决了。

所以本文档的结论是：**不要继续在现有链路上打补丁，而是新增一个专门的定位工具。**

## 四、需要什么样的工具

### 核心原则

> **识图只负责"理解"，坐标必须由工具给出。**

模型看图，回答"这是哪个关卡""这个界面是什么状态"。
模型**不应该**回答"这个按钮在第 1063 像素"——它根本答不准。

### 功能需求

#### 需求 1：精确坐标查询（最重要）

**做法：模板匹配。**

```
game_find({
  template: <一块小图，或之前存过的名字>,
  region?: {x, y, w, h},   // 可选，限定搜索范围，提速
  threshold?: 0.8           // 匹配阈值
})
→ [{ x, y, w, h, score }, ...]   // 精确到物理像素
```

**为什么模板匹配合适**：

- 游戏 UI 是像素确定的，同一按钮每次长得一样
- 全图搜索用 C# 实现，几千乘几千的图几毫秒到几十毫秒
- 不依赖 OCR，不挑语言
- 模板可以"录一次反复用"：第一次由我框出区域，工具存下来作为命名模板

#### 需求 2：带坐标标注的截图（辅助）

现在的截图返回给模型时，只有一行文字说明尺寸。
**问题是我经常记错缩放比。**

改进：

```
game_shot({ ..., overlay: true })
→ 图上画网格线 + 坐标刻度（每 100 或 200 像素一条）
→ 返回文字里明确写：原图 2560×1440，显示缩放 0.5，图内 1 像素 = 2 物理像素
```

这样我读大目标时可以直接对着网格读，不用心算。

#### 需求 3：文字/数字读取（后期）

固定区域（关卡名、评价 S/A/B、数值）如果能直接读出文字，比看图可靠得多。

可以用 Windows 自带的 OCR（`Windows.Media.Ocr`），中文支持良好，不需要装第三方。
**但优先级最低**——先把坐标问题解决。

## 五、坐标系统一方案

### 唯一坐标系：虚拟桌面物理像素

```
虚拟桌面 = 所有显示器拼起来的矩形
           单位：物理像素
           左上角可能是负数（副屏在左侧时）
```

**为什么选它**：

- Windows 内部所有窗口坐标、鼠标坐标都以它为基准
- 天然覆盖所有屏幕，不需要为"单屏 / 多屏"写两套逻辑
- 副屏的负坐标是合法值，不是异常

**单屏时它会退化成"主屏物理矩形"**，所以不需要特判。

### 只在这几处转换

| 场景 | 转换 |
| --- | --- |
| `GetClientRect` → 窗口物理尺寸 | `× (DPI / 96)` |
| 窗口内坐标 → 屏幕绝对坐标 | `+ 客户区在原点的偏移（已换算成物理）` |
| 屏幕绝对坐标 → `SendInput` 归一化 | `(x - virtualLeft) / (virtualWidth - 1) × 65535` |

**除此之外，全链路不再有别的换算。**

### 兼容性检查表

改完后必须满足：

| 场景 | 预期 |
| --- | --- |
| 单屏 + 100% 缩放 | 所有缩放系数为 1，公式退化，行为与旧版完全一致 |
| 单屏 + 125% 缩放 | 窗口物理尺寸正确，点击准确 |
| 主屏 + 右侧副屏 | 虚拟桌面 left=0，宽度=两者之和 |
| 主屏 + 左侧副屏（当前） | 虚拟桌面 left 为负，副屏坐标 x 为负 |
| 主屏 + 上下副屏 | 虚拟桌面高度变化，y 方向同理 |
| 不同屏幕不同缩放 | 每个窗口按自己所在屏的 DPI 计算 |
| 拔掉副屏 | 虚拟桌面自动缩小，代码无需改动 |

## 七、一路踩过的坑（避免重复）

### 坑 1：以为"多屏就是坐标错"

真相：多屏确实让 `MouseMoveAbs` 的分母错了，但**真正的痛点是读坐标不准**。
修坐标转换，解决不了"我看图报错数字"这件事。

### 坑 2：以为 Sunshine 劫持了鼠标

断开 Moonlight 后光标依然不动，说明不是它。
（真正原因：我自己的 PowerShell 进程没有桌面输入权限，`SetCursorPos` 静默失败。）

### 坑 3：以为手进程加载了新代码

日志显示手在正常连、正常编译，但名片里的 pid 和实际进程对不上。
**改完代码必须先确认手真的重启并加载了新版**，否则测的是旧逻辑。

### 坑 4：C# 里调用了没声明的 P/Invoke

`GetDpiForWindow` 没写 `DllImport`，PowerShell 语法检查查不出来，`Add-Type` 才报错。
**改完 C# 代码必须真的编译一次**，不能只看语法。

### 坑 5：用缩放过的宫格估坐标

`game_do` 返回的宫格、`game_shot` 的预览，都是**缩放过的**。
拿宫格上的像素位置直接当坐标，必然错。必须先换算回原图尺寸。
**而这件事我反复做错。**

### 坑 6：任务管理器的陷阱

Zzzz 不要用 `Get-Process -Name` 判断手是否存活——名字可能对不上。
要以 `hand.json` 名片 + 实际进程 + 日志的 `CONNECTED` 三处一致为准。

## 八、建议的实施顺序

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| **1** | 坐标系重构（虚拟桌面物理像素），**但只改代码、不改行为边界** | 无 |
| **2** | 加 `game_find` 模板匹配工具 | 阶段 1 |
| **3** | `game_shot` 加网格标注 + 明确的尺寸说明 | 无（可提前） |
| **4** | OCR 读取固定区域文字 | 阶段 2 |

### 阶段 1 的验收标准

不能只看"能不能点中"，要**量化**：

```
给一个已知坐标 (x, y) → 移动鼠标 → 读回光标实际位置 → 误差 ≤ 2 像素
```

**多个位置都要测**：左上、右上、左下、右下、中心，共 5 个点。
全部通过才算完成。

### 阶段 2 的验收标准

```
截一张图 → game_find 找「入梦」按钮 → 返回坐标
→ 用这个坐标点击 → 成功进入战斗
```

## 九、还没想清楚的问题

1. **模板怎么录？** 手动框选一块区域存成 PNG，还是让工具自动切？
2. **窗口不在 (0,0) 时怎么办？** 现在的测试都在 (0,0)，挪动窗口后是否正确未验证。
3. **副屏上的目标能否操作？** 理论上可以（虚拟桌面坐标覆盖副屏），但没有测试场景。
4. **`SendInput` 的归一化到底是按虚拟桌面还是按主屏？**
   MSDN 的说法是虚拟桌面，但**必须实测**——这决定了 `MouseMoveAbs` 的分母。
5. **游戏用 raw input 时，绝对坐标点击是否可靠？**
   README 里提到"鼠标相对移动受 raw input 影响需标定"，绝对坐标可能也有类似问题。
